# Задание 1. Проектирование технологической архитектуры

1. Стратегия масштабирования и отказоустойчивости

- Масштабирование:
  - Тип: горизонтальное масштабирование (Kubernetes HPA + Cluster Autoscaler)
  - Обоснование: автоматическое добавление подов и нод
- Отказоустойчивость:
  - Зоны доступности: использование 2 зон доступности (например, Москва и Екатеринбург), разделение на публичную/приватную зоны (Security Groups)
  - Цель: обеспечение непрерывности работы в случае сбоя в одной из зон
- Дополнительные зоны безопасности:
  - Публичная зона: веб-приложение, API для партнёров (доступ через Load Balancer)
  - Частная зона: БД, внутренние сервисы (информация о клиентах, расчёт страховых выплат)
  
2. Развертывание в нескольких зонах безопасности

- Конфигурация Kubernetes
  - Тип кластера: независимые кластеры в каждой зоне
  - Обоснование: нет зависимости от задержек между зонами, при падении одной зоны вторая останется рабочей
- Балансировка нагрузки 
  - Решение: GSLB - Yandex Application Load Balancer + DNS (маршрутизация по ближайшей зоне)
  - Обоснование: распределение трафика между зонами, минимальная задержка, мониторинг доступности зон (проверка работоспособности), ограничение Rate Limiting
- Фейловер-стратегия
  - Тип: Active-Active
    - Для фронтенда: 
      - трафик распределяется между зонами, учитывая доступность и задержку
      - при сбое GSLB перенаправляет трафик на оставшиеся зоны
      - в случае полного отказа основной зоны включается аварийное переключение DNS на резервные зоны
    - Для БД:
      - PostgreSQL + Patroni: автоматический переход на реплику при падении мастера
- Конфигурация базы данных
  - Тип базы данных: PostgreSQL 
  - Репликация (Patroni): 
    - 1 мастер (для 1 зоны) + 1 синхронная реплика (для каждой новой зоны)
    - Автоматическое переключение и восстановление
    - Согласованность и целостность данных
    - Хранение состояния кластера
    - Мониторинг доступности нод
  - Резервное копирование: pgBackRest — решение для резервного копирования и восстановления для PostgreSQL

3. Шардирование БД

- Шардирование пока не нужно (объём данных — 50 GB, PostgreSQL справится)
- Будущее решение:
  - Шардировать по региону клиента (например, client_info разделяется на шарды: Москва, Екатеринбург)
