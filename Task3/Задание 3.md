# Задание 3. Переход на Event-Driven архитектуру

1. Проблемы текущей архитектуры

- Синхронные запросы к сервису ins-product-aggregator:
  - Задержки при агрегации данных из 5 страховых компаний
  - Ошибки API страховых компаний влияют на доступность сервиса
  - Локальные реплики данных в сервисах core-app и ins-comp-settlement устаревают

- Периодические вызовы REST API:
   - сервис core-app запрашивает данные каждые 15 минут из сервиса ins-product-aggregator → возможны задержки
   - сервис ins-comp-settlement раз в сутки получает страховки из сервиса core-app и данные из сервиса ins-product-aggregator → риск потери данных при сбое

- Планируемый рост нагрузки:
   - Добавление 5 новых страховых компаний увеличит нагрузку на ins-product-aggregator
   - Синхронные запросы станут узким местом

2. Предлагаемые изменения

- Event-Streaming для сервиса ins-product-aggregator:
  - сервисы core-app и ins-comp-settlement асинхронно запрашивают информацию по страховым продуктам через Kafka топик у сервиса ins-product-aggregator 
  - сервис ins-product-aggregator читает топик запросов от сервисов core-app и ins-comp-settlement и опрашивает системы страховых компаний на получение данных по страховым продуктам.
  - затем сервис ins-product-aggregator публикует данные по страховым продуктам в Kafka топик
  - сервисы core-app и ins-comp-settlement подписываются на топик и обновляют данные в БД при получении событий

Примечание: Нельзя, чтобы сервис ins-product-aggregator самостоятельно с какой-то периодичностью опрашивал системы страховых компаний и публиковал события в Kafka топик.
Это может привести к тому что сторонние системы взаимодействие с которыми идет через REST / SOAP / GraphQL могут не выдержать нагрузки. 
Поэтому инициатором взаимодействия должны выступать по прежнему сервисы core-app и ins-comp-settlement.

- Event-Streaming для сервиса core-app:
  - сервис core-app при оформлении страховки будет публиковать это событие в Kafka топик
  - сервис ins-comp-settlement читает топик и сохраняет у себя информацию об оформленных страховках

- Паттерн Transactional Outbox (для надежной отправки событий):
  - сервис ins-product-aggregator прежде чем отправить событие в Kafka топик будет сохранять данные в БД. Сервис core-app уже это делает.
  - отдельный процесс будет читать записи и отправлять события в Kafka. Это гарантирует, что события будут отправлены только после успешного сохранения данных
